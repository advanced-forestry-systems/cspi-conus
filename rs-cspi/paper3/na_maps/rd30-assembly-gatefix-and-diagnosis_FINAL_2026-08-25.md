# RD30 CONUS assembly, job 13728908, diagnosis and gate fix

*25 August 2026. Track D of the same-day OODA pass on the North America CSPI/RD finalization effort. Reads the actual SLURM log for job 13728908 and the actual staged R script on Cardinal, not the narrative memos about them, per the assignment.*

## Headline

Job 13728908 did not crash and is not running. It ran cleanly through all 24,544 tiles and stopped on its own pre-registered F5 magnitude gate at a mapped area of 356.7 Mha against a hard window of [100, 350] Mha, an overshoot of about 2 percent against the upper bound. Every workspace document that still calls 13728908 "running," including this morning's synthesis memo, is wrong and is corrected here. A rebuilt assembly script implementing red team findings A1, A2, C1, C2, and C3 went through two more revisions this session (one fixing a real GDAL package/environment mismatch, one fixing a real shell-quoting bug in the mosaic-build step, both previously invisible because no run had ever gotten far enough to hit them) before completing all the way to the new A1 hard gate, which then correctly caught a genuine, previously undetectable defect: the assembled map's median at the 123,173 actual FIA plot locations is 0.766, against a plot RD_field median of 0.697, a 9.9 percent relative overshoot the project's other six gates cannot see. Neither product is promoted. This is the pipeline working as designed, not a new failure to route around.

## Diagnosis

`cardinal_job_status` for 13728908 returns FAILED, elapsed 00:31:11, started 2026-08-19T05:49:53, ended 2026-08-19T06:21:04, exit code 1:0. The 31-minute elapsed time against a 12-hour walltime rules out a timeout. The staged stderr log, `Disturbance_run/alphaearth/logs/rd30-assemble-qm2-13728908.err`, holds exactly one line:

`Error: GATE FAIL (F5 magnitude): mapped area 356.7 Mha outside [100,350]; external anchor FIA CONUS forest ~251 Mha`

The matching stdout log confirms the run got all the way through the pipeline before that stop: the F9 units-chain gate passed (RD_field median 0.697 against the 0.6970 anchor), the rev-2 QM distribution-match gate passed (mapped sample median 0.698 against plot median 0.697), all 24,544 tiles were read, LUT-applied, and written with zero tile errors, and the calibrated mean landed at 0.8365, inside rev 2's own tightened [0.75, 1.13] value window. Only the area check failed. This is a legitimate, correctly-firing gate stop, not a bug, not an R error, and not the same failure class as rev 1 (job 13728887), which failed on an unrelated LUT-range gate bug that rev 2 had already fixed by capping the LUT domain and codomain at 1500 (RD 1.5) and replacing the raw LUT-max check with a distribution-match check.

The root cause of the stop is that the F5 window's anchor conflates two different populations. The gate counts every pixel with a positive calibrated RD value as "mapped area," then compares that pixel count against FIA's closed-canopy forestland estimate for CONUS (about 251 Mha). Those are not the same population by construction. The calibrated tile mask is whatever the upstream route_a hex-SAE pipeline retained, which plausibly includes mixed pixels, forest edges, recently disturbed cells, and wooded non-forest inside the tile footprint, none of which the FIA plot network samples as forestland. This is exactly the pixel-population-versus-plot-population gap the 19 August red team already flagged in finding C1 for the quantile-mapping design, now showing up a second time in the area gate. Rev 2 inherited rev 1's [100, 350] window unchanged even though the same red team pass called it "wider than plus or minus 40 percent" and therefore already generous, yet the actual run still cleared it by only 2 percent on the wrong side. No document in the workspace derives what the RD-positive mask area should be as distinct from FIA forestland, so there is no defensible number to re-derive the window from today. Widening the bound without that derivation would be exactly the kind of unanchored gate the red team's A2 finding already criticized in a different context, so this pass does not do that. Instead it demotes F5 to an informational, non-blocking measurement and installs a new gate, A1, that tests the thing that actually matters: whether the assembled map, read back at the locations FIA actually measured, reproduces the value FIA actually measured.

## A1, A2, C1, C2, C3: fixes applied

**A1 (must-fix, implemented as a new hard gate).** The red team's strongest finding was that no rev-1/rev-2 gate could catch a defect already baked into the tiles before assembly, since every gate either reads the input plot table, counts files, or checks that the mosaic faithfully reproduces its own (possibly wrong) tiles. Rev 3 adds a gate that extracts the assembled calfix mosaic at the plot (mx, my) locations carried in the restricted `_private/sae_plot_enriched.csv`, server-side on Cardinal, and requires the sampled median to sit within 0.02 of the plot RD_field median (0.6970), the same tolerance F9 already uses. No coordinate and no per-plot extracted value is printed, logged, or written to any file at any point in the script; only the aggregate median and sample size are recorded, in the gate report and in stdout. This directly answers the adversarial scenario the red team posed (a repeat of the 2.471x-class constant multiplicative defect) in a way area counts and 3-tile identity draws cannot. A companion informational check computes the pixelwise ratio of the new calfix value against the quarantined pre-fix stale raster (`conus_RD_30m_SAEcal_2022_STALE_PREV_20260708.tif`, itself measured at exactly 2.471 low, see `QUARANTINE_README.txt`) at the same sampled cells, logged but not hard-gated, since that raster came from a different calibration pass and an exact 2.471 match is not guaranteed even on a fully correct run.

**A2 (must-fix, documentation added).** Rev 2 had already moved off the unanchored raw-LUT-max-3000 gate rev 1 failed on, capping the LUT domain and codomain at 1500 (RD 1.5) to match the 12 August two-product ceiling decision, and replacing it with the distribution-match gate. What rev 2 never stated was which quantile of the target RD_field distribution that cap corresponds to. Rev 3 computes and logs it directly: `q_at_cap <- mean(rdf <= 1.5)`, printed every run as "A2 anchor: product/LUT cap RD=1.5 sits at RD_field empirical quantile X." This replaces an implicit, unstated derivation with an explicit, reproducible one, without changing the ceiling decision itself, which remains out of scope for this pass.

**C1 (must-fix, metadata expanded).** Rev 2 already carried a one-line "display only" tag on the qmap product. Rev 3 expands the GDAL metadata on `conus_RD_30m_qmap_2022.tif` with four explicit tags: that the layer reproduces the national plot RD_field ECDF by construction and only at the national aggregate level, that it is not validated for subnational or regional distributional claims (the review's own example, share of forest above a threshold RD in a named region), and that the 12 August held-out validation covered the plot-space transform (OOF plot predictions mapped to plot field values) rather than this pixel-space transform (map pixel ECDF mapped to plot ECDF), attributed to the 19 August red team finding.

**C2 (should-fix, documented rather than rebuilt).** The concern was that a large input-side point mass at the 1.5 cap, combined with monotone cummax construction, could pin the entire capped mass to an outlier-driven value near the RD_field maximum (6.3686). Rev 2's target-side cap at 1500 already prevents that specific failure mode structurally, since LUT output can never exceed 1.5 regardless of what quantile the input point mass maps to. What was missing was documentation. Rev 3 logs the fraction of sampled pixels sitting at the input cap and confirms the deterministic LUT value that point mass maps to (`LUT[1500]`, necessarily 1500, the output cap), so the tie rule is now stated rather than an unexamined side effect of `cummax`. Building the LUT from uncapped upstream values, the review's other option, was not attempted: the calibrated tiles are already capped at source (route_a job 13566048), and no uncapped upstream layer is staged, so that option is not available within this pass and is carried to the unknowns ledger rather than faked.

**C3 (should-fix, implemented).** The every-25th-tile stride for the distribution sample is replaced with a seeded random draw of the same number of tiles (`set.seed(42)`, already the script's seed, extended to this draw). This removes the row-major striping risk the review raised without needing to compute the tile grid's row width or check its gcd with 25, which the tile filenames do not straightforwardly expose. The residual assumption the review also raised, that whole-tile sampling weights the ECDF by within-tile forest pixel count, is not fixed here and is carried to the unknowns ledger, since checking it needs a per-tile pixel-count series nothing in this pipeline currently computes.

**A3 (note, added as a free check).** Spearman correlation between the calfix and qmap layers at the same plot-adjacent sample is logged, informational, expected near 1.0 since quantile mapping is monotone by construction.

## New job status: four more jobs ran this session

Getting a verdict out of the rebuilt pipeline took four more Cardinal jobs, two of them unrelated infrastructure fixes. All four are reported in full since two surfaced genuine, previously undocumented defects.

Job 13958796 (`rd30-assemble-qm3`, first submission) failed in 2 seconds, before any gate: `terra` could not load, `libgdal.so.39: cannot open shared object file`. `terra.so` was rebuilt 2026-08-20, the day after job 13728908 ran successfully on the identical module stack, so the personal library's `terra` had been reinstalled against a newer GDAL ABI than Cardinal's only available module (`gdal/3.7.3`; confirmed via `module spider gdal`). Fix: job `terra-relink` (13958888) reinstalled `terra` from source against the loaded modules, completed in 6:17, smoke test passed (terra 1.9-46). Additive change to the user's own R library, no deletion, no other package touched.

Job 13959149 (rev 3 resubmitted) ran 37:34 and got further than any prior RD30 job: F9, the new A2/C2 diagnostics, the C3 random-tile QM gate, all 24,544 tiles with zero errors, the F5 informational log (356.7 Mha, identical to 19 August), and the value-mean gate all passed. It then crashed building the first mosaic: `sh: -c: syntax error near unexpected token '('`. R's `system2()` does not shell-quote its `args` vector, and the METHOD metadata tag's parentheses and commas, plus the plain space-separated `UNITS=RD x 1000 INT2S` tag, were handed to the shell unquoted. This exact bug existed verbatim in rev 1 and rev 2 but never fired, since both failed at an earlier gate before ever reaching `build()`; downgrading F5 is what first exposed it. Fix verified standalone (`system2("echo", c("-mo", shQuote(m)))` preserved the string intact) before being applied as `rd30_assemble_qm4.R`, wrapping every `-mo` value in `shQuote()`.

Job 13960109 (rev 4) ran 1:13:12 and is the first job in this family to reach mosaic-build successfully: both GeoTIFFs wrote cleanly and the cross-layer identity gate passed for both products. It then hit the new A1 hard gate, and this is a real finding, not a bug: **the calfix mosaic sampled at the 123,173 actual FIA plot locations has a median of 0.766 against the plot RD_field median of 0.697, an absolute difference of 0.069 (9.9 percent relative), exceeding the 0.02 tolerance.** Stderr: `GATE FAIL (A1 plot anchor): ... diff 0.069 exceeds 0.02 tolerance`. Both products remain `_PROVISIONAL` on disk (calfix 4.80 GB, qmap 3.88 GB, written 25 August), never renamed, per the project's PROVISIONAL-until-gates-pass convention. `rd30_assembly_gate_report.csv` was not written since that write sits after promotion in the script and A1's `stop()` fires first; the full trace lives only in the stdout/stderr log, a minor robustness gap for a future revision (write the report incrementally).

This is exactly the defect class A1 was built to catch and no prior gate could see: the value-mean gate passed at 0.8365, a population-wide statistic over 3.96 billion pixels, while A1 checks the map's own median specifically at the 123,173 locations with ground truth. A working hypothesis, not a conclusion (full reasoning in the unknowns ledger): RD_field is right-skewed, and a hex-SAE calibration fit to correct bias in the mean would not be guaranteed to correct the median. No rev 5 was attempted. Loosening the 0.02 tolerance to force a pass would repeat exactly the unanchored-gate mistake the red team criticized in A2, so that was not done; the correct next step is diagnosing the gap, not relaxing the number that caught it.

## Unknowns ledger

Known known: the F5 stop on 19 August was a legitimate gate firing on real data, not a script defect, confirmed from the actual stderr and stdout rather than inferred from elapsed time or exit code alone.

Known known: the pipeline itself, tiles through mosaic assembly, is mechanically sound. All 24,544 tiles processed with zero errors across two full runs (rev 3 and rev 4, identical results: area 356.7 Mha, mean_cal 0.8365, mean_qm 1.0184, bit-for-bit reproducible under the shared seed), both mosaics wrote correctly, and both passed the tile-level cross-layer identity check. The A1 failure is not an artifact of assembly mechanics.

Live known unknown, the most important item in this ledger: why the calfix mosaic reads 0.766 at plot locations against a plot RD_field median of 0.697, a 9.9 percent relative gap. Three candidate explanations, none yet tested. First, the hex-SAE calibration may correct bias in the mean rather than the median within each hex; RD_field is right-skewed (plot mean 0.9424 against plot median 0.6970), so a mean-correct calibration is not guaranteed to be median-correct, and A1 is the first gate ever to check the median specifically at plot locations rather than a population-wide mean. Second, the (mx, my) extraction could be pulling a neighboring pixel rather than the plot's own forest pixel if the coordinate pair is not pixel-registered to the exact tile grid the way this pass assumed; this was not independently verified, only assumed reasonable from the column-naming convention. Third, a residual, smaller-magnitude version of the defect class this entire correction chain exists to catch cannot be ruled out from this run alone. Distinguishing these needs, at minimum, the distribution of per-plot residuals (not just the median), a check of extraction pixel registration against a handful of known hex boundaries, and possibly a rerun of hex-SAE calibration with an explicit median-matching criterion. None of this was attempted in this pass; the gate correctly stopped promotion instead of guessing.

Known unknown, carried forward rather than resolved: no document anywhere in the workspace states what the RD-positive calibrated-pixel mask area should be, as distinct from FIA closed-canopy forestland. Deriving that number, plausibly from the route_a tile generation mask definition or an NLCD/tree-cover-class total, would let F5 be reinstated as a properly anchored gate rather than left informational. This is a real gap, not a rounding matter, since it is the same gap that produced the original 19 August stop.

Known unknown: whether whole-tile sampling for the distribution LUT (both the rev-2 every-25th scheme and this rev's seeded-random replacement) weights the ECDF by within-tile forest pixel count in a way correlated with the RD distribution itself. Nobody has checked this, per the red team's own C3 note, and the fix here (random tile selection) removes the spatial striping risk without touching this separate weighting question.

Known unknown: whether the hex-SAE calibration factors used to build the tiles were fit using these same 123,173 plots in a way that makes the A1 gate partially circular. The plot table A1 samples against (`_private/sae_plot_enriched.csv`) is the same one F9 already uses, and the calibration factors are indexed by hex rather than by individual plot, which limits but does not eliminate this concern. A1 remains the strongest available check with data already on Cardinal, and it directly tests the assembly stage (VRT construction, LUT application, GeoTIFF write) regardless of how the calibration itself was fit, but it is not a fully independent held-out test. Notably, if this were the sole explanation, it would predict A1 passing trivially rather than failing by 9.9 percent, which is itself evidence the gap is not pure circularity.

Unknown unknown surfaced this pass: the tile grid's row-major layout and its dimensions are not recorded anywhere read during this diagnosis, which is why the C3 fix went straight to random sampling rather than computing gcd(row width, 25) as the review's first-listed option.

Unknown unknown surfaced this pass, second instance: the `system2()`/shell-quoting bug in `build()` had been latent in every version of this script since rev 1 (19 August) and was invisible until this pass's F5 downgrade let a run reach that code path for the first time. This is a direct illustration of the red team's own A1 argument generalized. A gate that halts a pipeline early does not just block a bad product, it can also hide defects in code that never runs.

## Implementation notes

Deviation from the assignment's suggested approach: the red team's A1 wording offers extracting server-side against the OOF calibrated distribution or checking the stale-raster ratio as alternatives. This pass implements the plot RD_field median check as the hard gate and the stale-raster ratio as an informational diagnostic only, since the calibration pass that produced the stale raster differs from the current one and an exact 2.471 match is not a fair pass/fail bar.

Failed attempt: a `find / -maxdepth 6 -iname alphaearth` sweep to locate the working directory before the correct path was known timed out and was abandoned in favor of narrower, targeted `find` calls once `$HOME` was confirmed. The Cardinal connector's known instability (documented project-wide) surfaced repeatedly during this session as intermittent "Connection closed" errors on `cardinal_run` and `cardinal_list`, cleared by straightforward reissue per the project's standing working convention, with no timeout increases and no case requiring more than a handful of retries.

Deferred, not done in this pass: diagnosing the 0.069 A1 median gap (the live unknown above, and the actual next step for this track), deriving a defensible F5 area anchor, checking gcd(tile-grid row width, 25) directly rather than sidestepping it via random sampling, and rebuilding the LUT from uncapped upstream calibrated values, since no uncapped layer is staged anywhere this session located. None of these were fabricated a resolution to; all are legitimate, explicitly named follow-on work.

Two defects outside the original assignment were found and fixed mid-pass (terra/libgdal, job 13958888; the `system2()` shell-quoting bug, fixed in `rd30_assemble_qm4.R`), both detailed above. No job in the five-job chain (13728908, 13958796, 13958888, 13959149, 13960109) was cancelled or force-killed; each ran to its own natural stop.

No `rm` command was issued or is proposed. No file was deleted; the terra reinstall is additive to the user's personal R library and touches no other package. Compute stayed entirely on Cardinal throughout, consistent with RD30 touching FIA-derived plot data; no true FIA coordinate value, and no per-plot extracted raster value, was printed, logged, or transmitted off Cardinal at any point in this diagnosis or in any script version.
